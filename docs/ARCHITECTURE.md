| ตาราง | หน้าที่ | ใครเข้าถึงได้ |
|-------|---------|----------------|

| `listings` | ประกาศที่แปลงแล้ว | published + ไม่ซ้ำ = ทุกคน · ที่เหลือ = เจ้าของ/แอดมิน |
| `listing_duplicates` | คู่ที่ซ้ำ + คะแนน + เหตุผล | แอดมิน + เจ้าของประกาศที่เกี่ยว |

| `leads` | ผู้ซื้อที่กดติดต่อ | ผู้ซื้อ + ผู้ขายของประกาศนั้น |
| `saved_searches` | เงื่อนไขค้นหาที่บันทึกไว้ | ของใครของมัน |
| `geocode_cache` | แคชผลแปลงที่อยู่เป็นพิกัด | แอดมินอ่าน · เขียนผ่าน service role |
| `ingest_runs` | บันทึกรอบการนำเข้า | แอดมินอ่าน |
| `audit_logs` | ใครทำอะไรกับข้อมูล | แอดมินอ่าน |

### สิทธิ์ 3 ระดับ

| ทำอะไรได้ | ผู้ซื้อ | ผู้ขาย | แอดมิน |
|-----------|:------:|:-----:|:------:|
| ดูประกาศที่เผยแพร่แล้ว | ✅ | ✅ | ✅ |
| บันทึกรายการโปรด / ติดต่อผู้ขาย | ✅ | ✅ | ✅ |
| ลงประกาศ | ❌ | ✅ (ของตัวเอง) | ✅ |
| เผยแพร่ประกาศเอง | ❌ | ❌ | ✅ |
| เห็นข้อมูลดิบ / บันทึกการทำงาน | ❌ | ❌ | ✅ |
| รวม/แยกรายการซ้ำ | ❌ | ❌ | ✅ |
| เปลี่ยนบทบาทผู้ใช้ | ❌ | ❌ | ✅ |

**กันการยกระดับสิทธิ์ไว้ 3 ชั้น**
1. ทริกเกอร์ `handle_new_user` — สมัครสมาชิกขอเป็น admin ไม่ได้ บังคับเป็น buyer/seller
2. ทริกเกอร์ `profiles_guard_privileges` — ผู้ใช้แก้ `role` ของตัวเองไม่ได้
3. ฟังก์ชัน `merge_duplicate` / `unmerge_duplicate` เป็น SECURITY DEFINER
   จึงตรวจ `is_admin()` ในตัวฟังก์ชันเอง ไม่พึ่ง RLS อย่างเดียว

## ท่อลำเลียงข้อมูล (`lib/ingest.ts`)

```
โพสต์เข้ามา
   │
   ├─ ชั้นที่ 1 ── content hash ── โพสต์เดิมจากแหล่งเดิม? ──▶ ข้าม
   │
   ├─ ชั้นที่ 2 ── parsePost() ── ไม่ใช่ประกาศขาย? ──────▶ คัดออก
   │                              (โพสต์ตามหา / ไม่มีราคา / ไม่มีช่องทางติดต่อ)
   │
   ├─ เติมพิกัด GPS ตามลำดับความน่าเชื่อถือ
   │     1. พิกัดในข้อความโพสต์          → exact
   │     2. ลิงก์ Google Maps ย่อ         → exact  (ตามลิงก์ไปหาพิกัดจริง)
   │     3. Google Geocoding API         → rooftop / geocoded
   │     4. จุดกึ่งกลางตำบล/อำเภอ         → subdistrict / district (คร่าว ๆ)
   │
   ├─ บันทึกเป็นประกาศ (สถานะ "รอตรวจสอบ")
   │
   └─ ชั้นที่ 3 ── ให้คะแนนความซ้ำ ──▶ ≥85 รวมอัตโนมัติ
                                    ──▶ 60-84 ส่งแอดมินตัดสิน
                                    ──▶ <60 ถือว่าไม่ซ้ำ
```

## ตัวแยกข้อมูลภาษาไทย (`lib/parser/`)

โพสต์อสังหาฯ ไทยเขียนกันหลากหลายมาก ตัวแยกข้อมูลจึงต้องรับมือกับ

| เขียนแบบไหน | อ่านได้เป็น |
|-------------|-------------|
| `4.65 ล้าน` · `๒,๑๕๐,๐๐๐` · `ราคา 2.39` | 4,650,000 · 2,150,000 · 2,390,000 |
| `ไร่ละ 3.5 ล้าน` + `2 ไร่` | 7,000,000 (คูณให้) |
| `ตารางวาละ 12,000` + `1 ไร่ 2 งาน` | 7,200,000 |
| `1 ไร่ 2 งาน 30 ตร.ว.` | 630 ตารางวา |
| `3 นอน 2 น้ำ` · `3 ห้องนอน` | ห้องนอน 3 ห้องน้ำ 2 |
| `๐๘๖-๕๕๕-๑๒๑๒` · `+66865551212` | 0865551212 |
| `ต.บ้านพรุ` · `ใกล้ ม.อ.` | ตำบลบ้านพรุ · คอหงส์ (จากแลนด์มาร์ก) |
| `maps.app.goo.gl/xxx` | ตามลิงก์ไปหาพิกัดจริง |

**จุดที่ต้องระวังเป็นพิเศษ** (แก้ไปแล้วและมีเทสต์คุม)
- `ราคาไร่ละ 3.5 ล้าน` ต้องไม่ถูกอ่านเป็นราคารวม — ปิดบังข้อความส่วนนั้นก่อนหาราคารวม
- `เหมาะปล่อยเช่านักศึกษา` ในประกาศ **ขาย** ต้องไม่ถูกจัดเป็นประกาศให้เช่า
- `มีใครขายบ้านแถวหาดใหญ่บ้างครับ` เป็นโพสต์ **ตามหา** ต้องคัดออก ไม่ใช่ประกาศ

ทดสอบด้วย `npm run test:parser`

## อัลกอริทึมคัดข้อมูลซ้ำ

คำนวณในฐานข้อมูล (`find_duplicate_candidates`) เพื่อความเร็วและใช้ index ได้เต็มที่

| หลักฐาน | คะแนน |
|---------|-------|
| เบอร์โทรตรงกัน | +40 |
| ราคาต่างกันไม่เกิน 2% | +18 |
| เนื้อที่ต่างกันไม่เกิน 3% | +14 |
| พิกัดห่างกัน ≤ 300 ม. | +16 |
| พิกัดห่างกัน ≤ 500 ม. | +8 |
| **พิกัดห่างกัน > 1 กม. ทั้งที่แม่นทั้งคู่** | **−30** |
| ความคล้ายข้อความ (trigram) | + สัดส่วน × 32 |
| ประเภททรัพย์เดียวกัน / ต่างกัน | +4 / −25 |

**ทำไมต้องมีคะแนนติดลบ** — นายหน้าคนเดียวกันมักขายหลายหลังในราคาและขนาดใกล้เคียงกัน
ถ้าให้คะแนนแต่ด้านบวก ทรัพย์คนละหลังจะถูกรวมเป็นรายการเดียว ประกาศจริงจะหายไปจากระบบ
คะแนนติดลบเมื่อพิกัดห่างกันมาก **และเชื่อถือได้ทั้งคู่** จึงจำเป็น

ตัวอย่างจากการทดสอบจริง: ทาวน์โฮมคนละโครงการของนายหน้าคนเดียวกัน ราคาและขนาดเท่ากัน
ห่างกัน 5.3 กม. → ได้ 67 คะแนน (ส่งแอดมินตัดสิน) แทนที่จะเป็น 97 (รวมอัตโนมัติ)

**เกณฑ์ตั้งไว้เข้มด้านการรวม** เพราะการรวมผิดทำให้ประกาศจริงหายไป
ซึ่งเสียหายกว่าการปล่อยรายการซ้ำหลุดมาให้แอดมินเก็บทีหลัง
และการรวมทุกครั้ง **ไม่ลบข้อมูล** — แค่ทำเครื่องหมาย `duplicate_of` ยกเลิกได้เสมอ

## การแสดงตำแหน่งอย่างซื่อตรง

ประกาศส่วนใหญ่ไม่ได้บอกพิกัดจริง ระบบจึงแยกความแม่นยำเป็น 6 ระดับ
และ **แสดงผลต่างกันบนแผนที่**

| ระดับ | ที่มา | แสดงอย่างไร |
|-------|-------|--------------|
| `exact` | ผู้ขายปักหมุด / พิกัดในโพสต์ | หมุดป้ายราคาสีเข้ม |
| `rooftop` | Geocoding ระดับบ้านเลขที่ | หมุดป้ายราคาสีเข้ม |
| `geocoded` | Geocoding ระดับถนน/ซอย | หมุดป้ายราคาสีเข้ม |
| `subdistrict` | จุดกึ่งกลางตำบลโดยประมาณ | **วงพื้นที่รัศมี 900 ม.** + ป้ายเส้นประ |
| `district` | จุดกึ่งกลางอำเภอโดยประมาณ | **วงพื้นที่รัศมี 3 กม.** + ป้ายเส้นประ |
| `unknown` | หาตำแหน่งไม่ได้ | ไม่ขึ้นบนแผนที่ |

หน้ารายละเอียดของประกาศที่ตำแหน่งไม่แม่นจะมีข้อความกำกับชัดเจนว่า
เป็นตำแหน่งโดยประมาณ ไม่ใช่ที่ตั้งจริง

> พิกัดกึ่งกลางตำบล/อำเภอใน `lib/parser/gazetteer.ts` เป็นค่าประมาณ
> ใช้เป็นทางสำรองเมื่อไม่มี Geocoding API เท่านั้น
> ควรแทนที่ด้วยข้อมูลขอบเขตการปกครองจากกรมการปกครองเมื่อใช้งานจริงจัง

## ประสิทธิภาพ

- **Index** ครอบทุกรูปแบบการค้นหาจริง: สถานะ+เวลา, พิกัด, ราคา, ประเภท, อำเภอ,
  เบอร์โทร (จับซ้ำ) และ GIN trigram สำหรับค้นข้อความไทย
- **ค้นหาด้วยคิวรีเดียว** — `search_listings` คืนทั้งผลลัพธ์และจำนวนรวม
  ผ่าน `count(*) over ()` ไม่ต้องยิงคิวรีนับแยก
- **แผนที่หน่วงคำขอ 350 มิลลิวินาที** ตอนผู้ใช้ลากแผนที่ และทิ้งผลลัพธ์ของคำขอที่ถูกแทนที่แล้ว
- **แคชผล geocoding** ในฐานข้อมูล รวมถึงกรณี "หาไม่เจอ" เพื่อไม่ยิง API ซ้ำ
- **รวมกลุ่มหมุด (clustering)** ทำให้แสดงประกาศหลักพันรายการบนมือถือได้ลื่น
